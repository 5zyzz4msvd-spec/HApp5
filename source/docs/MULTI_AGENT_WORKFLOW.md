# 多 Agent 轻量工作流

目标：把单个臃肿工作流拆成按需协作的专门 agent。每次只启动相关 agent，统筹 agent 负责裁剪上下文、合并补丁和验证，不让所有 agent 都读全量脚本/世界书。

## 总原则

1. 统筹 agent 是唯一入口。它读用户需求、`docs/PROJECT_STATE.md` 和本文档，然后决定需要哪些专门 agent。
2. 专门 agent 只读自己的锚点文件和统筹给的任务合同，不读完整聊天历史，不读无关生成物。
3. 变量名和写入路径先定合同，再让世界书、前端和脚本消费；不要让各 agent 各自发明字段。
4. 只有统筹 agent 合并代码、运行构建/验证、提交/发布。专门 agent 输出补丁建议或局部实现，不单独发布。
5. 每个 agent 的输出必须短：变更点、文件/锚点、风险、需要的验证。不要粘贴整段世界书或整份 HTML。
6. 所有 agent 用完即释放：统筹 agent 在合并结论或确认无需继续等待后必须关闭已完成/不再需要的 agent，避免占用后续任务位置。
7. 一次性弹窗、剧情线解锁、前端自动修复等状态机必须先写清“触发条件、状态迁移、重复进入、失败回滚、旧聊天补缺”五件事；状态未落盘前不要让 UI 假定迁移成功。
8. 同一按钮同时改 MVU、角色卡世界书和暂存区时，按一个跨资源事务设计：先记录原状态，逐步写入，任一步失败就回滚本次新增；已有同名角色或世界书条目只跳过/重新启用，不覆盖用户内容。
9. 简单单层任务不要为了“多 agent”而启动子 agent；统筹先完成阻塞性本地检查，再按文件边界启动必要 agent。
10. 任何 agent 发现当前文档与 `docs/PROJECT_STATE.md` 的变量合同冲突时，先回报统筹，不按旧文档继续实现。

## 统一任务合同

统筹 agent 分发任务时只给这 8 项：

```text
需求摘要：
涉及层级：变量 / 世界书 / EJS / 前端正则 / 酒馆助手脚本 / Git发布
已确认变量合同：
相关文件：
必须保留：
必须删除或禁止：
验证点：
开放问题：
```

任务合同里的“必须删除或禁止”只写工程禁项，例如旧路径、旧脚本、重复规则、错误发布目标；不要写和本次实现无关的口径。

专门 agent 返回：

```text
结论：
建议改动：
文件锚点：
兼容/风险：
验证命令：
是否需要其他 agent：
```

## 1. 统筹 Agent

职责：

- 拆需求，判断要不要启动其他 agent。
- 维护变量合同和跨层一致性。
- 合并专门 agent 的结论，避免重复规则和重复实现。
- 最后运行验证、提交或发布。

默认读取：

- `docs/PROJECT_STATE.md`
- `docs/MULTI_AGENT_WORKFLOW.md`
- 用户明确要求相关的文件锚点

禁止：

- 不把整份 `scripts/mirror-frontend.mjs`、`scripts/finalize-card-v1_6.mjs` 发给所有 agent。
- 不让多个 agent 同时修改同一段代码。
- 不在变量合同未定时让前端先写字段。

决策顺序：

1. 先问：这是变量合同变化吗？
2. 再问：AI 需要靠世界书理解吗？
3. 再问：前端是否需要按钮、暂存、localStorage、MVU 读写或正则入口？
4. 再问：酒馆助手脚本是否需要事件监听、自动修复或数值脚本？
5. 再问：是否涉及 EJS 动态提示、`getvar` 路径、变量列表输出或邂逅导入世界书？
6. 最后问：是否涉及 git 历史、发布远程、CDN、本地酒馆替换或删除聊天记录？
7. 最后只启动必要 agent，并在用完后关闭释放。

### 一次性状态与测试开场

- 前端拥有的整数剧情线必须在变量合同中列出当前实现的状态含义；未实现的后续状态只保留数值空间，不提前生成 UI、世界书或角色变量。
- `0 -> 1` 这类一次性触发要同时定义刷新/重开后的恢复入口。不能因为变量已经写成 `1`，就让尚未完成的确认按钮永久消失。
- 自动弹窗只挂载到所属应用根容器，且必须有内存级重入锁；MVU 写入失败时保留可重试状态，不把失败当成已完成。
- 角色变量、角色图片缓存、角色卡世界书和锁定暂存存在组合写入时，复用邂逅的“缺失才创建 + 失败回滚”语义，并在 payload 中注明哪些路径已由前端处理。
- 新增“开场白 N”测试入口时，验证主开场白与 `alternate_greetings` 的实际索引关系，并断言每个测试开场锚点只对应一个初始化脚本；不要只断言数组长度。
- 把旧静态功能迁移为“按钮后动态插入”时，finalizer 必须显式清除输入 PNG 中的孤儿世界书、脚本和旧变量根；验证要同时断言最终卡中旧实现缺席、生成前端中动态模板存在。
- 首楼开场选择、线路补写、邂逅导入这类前端写世界书的功能，必须优先复用现有完整模板源；找不到完整源时停止插入并报错，不生成缩略代用品。
- 一次性操作如果会写暂存区，必须定义“同一回合再次点击”的处理：禁用、覆盖、合并或提示；不要让重复暂存互相矛盾。

## 2. 变量 Agent

职责：

- 设计 MVU 字段、默认值、只读/可写规则、JSON Patch 路径。
- 维护 `[initvar]变量初始化不需要开`、schema、变量说明中的字段一致性。
- 判断字段应该由 AI 写、前端写、脚本写，还是只读派生。
- `extensible` / `recursiveExtensible` 只能按变量合同定点调整。不要为了修复单个动态字段，把无关对象或整棵 schema 改成可扩展；新增动态字典/数组时必须写明为什么允许扩展、扩展边界在哪里。
- schema 修改必须和 `stat_data` 默认结构同步：新增字段要同时检查默认变量、schema、变量格式检查/修复逻辑、旧聊天兼容修复和世界书路径说明；删除字段要确认前端、世界书、酒馆助手脚本和 EJS 不再读取。
- 动态对象优先只对明确的字典节点开启 `extensible`，例如任务、校规、持有物品这类“键名由内容决定”的对象；普通角色字段、系统固定字段、只读字段不要顺手开放。
- 动态数组如确实需要追加元素，必须明确数组元素 schema 和上限；不要把数组设成非扩展后又让 AI/前端输出 `/数组/0` 追加，也不要为了追加数组而放开无关父对象。
- 遇到 `SCHEMA VIOLATION` 时先判断是 JSON Patch 操作类型错误、路径错误、required/non-extensible 冲突，还是旧聊天 schema 没迁移；不要直接把整棵 schema 改成可扩展。
- 当前角色根必须按 `docs/PROJECT_STATE.md` 的十页合同核对：`衣着`、`信息`、`状态`、`事件`、`敏感`、`效果`、`劣迹`、`改造`、`物品`、`子嗣`。任何“七页”“档案对象”“根级状态散字段”的描述都视为旧资料。
- 金钱、MC 能量、星光点、VIP、任务/成就领取这类前端锁定操作，要在变量规则中明确“前端已结算时 AI 不重复扣加”；重 roll 场景要检查暂存快照是否会被再次结算。

主要文件：

- `scripts/mvu-schema-contract.mjs`
- `scripts/finalize-card-v1_6.mjs`
- `scripts/verify-card-release.mjs`

输出必须包含：

- 字段名和路径，例如 `/系统/_buff结束时间`
- 默认值
- 写入方：AI / 前端 / 酒馆助手脚本 / 只读派生
- 是否允许旧字段兼容
- 必须加入的验证断言

Schema 与验证硬要求：

- 当前 Schema 只能在 `scripts/mvu-schema-contract.mjs` 定义一次；finalizer 把同一份内容写入卡片，verifier 直接调用同一构造函数做正反例，禁止各维护一份近似结构。
- 成品 PNG 必须恰好有一份启用的 `registerMvuSchema` 脚本；旧 Schema 不论启用或关闭都要由 finalizer 清除。
- `[initvar]变量初始化不需要开`必须保持关闭，但其 YAML 必须能通过当前 Schema；关闭不是逃避结构验证。
- verifier 必须验证成品而非 finalizer 死代码：至少覆盖旧`档案`、跨页`信息/面部`、`状态/心理`、未知改造叶、错误性格形态、越界线路和无年份日期等拒绝样例。
- 变量列表无`mvu_plot`/`mvu_update`前缀，让两个模型共享；系统与角色当前快照用 D0，任务/校规/库存/课程表/地点按关键词使用 D1。蓝灯是常驻，绿灯是关键词触发，不能只改`constant`却忘记`selective`和关键词。
- 常驻 MVU 提示要设硬预算并由成品验证器统计；变量更新格式只保留一份规范封装，不重复十页合同。

边界：

- 不写 UI。
- 不写剧情解释。
- 不改酒馆助手事件脚本，除非只是指出需要脚本 agent 接手。

## 3. 世界书 Agent

职责：

- 维护角色卡世界书条目、AI 执行规则、好感链、角色人设和变量条目说明。
- 清理重复、过时、互相冲突的规则。
- 让世界书只解释必要规则，不塞前端已经处理的细节。
- 做规则压缩时优先删改旧句、冲突句和重复句；不要靠追加更多“注意事项”覆盖旧规则。

主要文件：

- `scripts/finalize-card-v1_6.mjs`
- `docs/邂逅世界书角色包工作流.md`，仅在处理角色包时读取

输出必须包含：

- 要改的 entry comment 或文本锚点
- 新规则摘要
- 删除/压缩了哪些旧规则
- 是否依赖变量 agent 的字段合同

边界：

- 不决定新变量名。
- 不写前端暂存结构。
- 不把只读变量塞进每轮 `<相关变量>`，除非变量 agent 明确要求。
- 不写发布说明、防盗说明、开发者署名、脚本原因、UI 实现细节或本地调试路径。

## 4. 正则/前端 Agent

职责：

- 维护手机/桌面前端、正则注入入口、首楼身份前端、暂存区、localStorage、MVU 读写、角色卡世界书前端管理。
- 用户说“正则”时也归此 agent，因为正则主要负责前端加载/注入。

主要文件：

- `scripts/mirror-frontend.mjs`
- `public/frontends/hypnosis-app/source.html`，只在源前端本身需要改时读取
- `scripts/finalize-card-v1_6.mjs` 中的 `regex_scripts` 生成段，仅当前端加载正则需要改时读取

输出必须包含：

- UI 状态变化
- MVU 读写路径
- 暂存区 payload 字段
- localStorage key/scope 是否新增或删减
- 前端存储导入/导出 schema 是否兼容旧版本字段
- 桌面端和手机端是否都需要重建
- 一次性状态机的触发条件、迁移、刷新恢复与失败回滚
- 同一次操作涉及 MVU / 世界书 / 暂存时的提交顺序和回滚范围

边界：

- 不改世界书叙事规则。
- 不新增变量名；只能消费变量 agent 给出的合同。
- 不手改生成出的 HTML，除非是验证输出；真实改动回到 `scripts/mirror-frontend.mjs`。
- 桌面模式里展示用的小按钮必须是非交互装饰；真实点击入口只保留在当前详情页，避免桌面卡片点击被隐藏按钮劫持。

### 事件委托与 `dataset` 防撞（强制）

注入式前端的页面根节点也会承载 `dataset` 状态；JavaScript 的 `page.dataset.fooBar` 会实际生成 `data-foo-bar` 属性。因此状态键绝不能与子控件事件选择器同名。例如，根节点的 `profileBadRecordTrait` 会生成 `data-profile-bad-record-trait`，从而与性格按钮 `[data-profile-bad-record-trait]` 冲突：点击在宿主/阴影边界被重定向时，`closest()` 会误命中根节点并把选择恢复成旧值。

- 状态键必须使用与控件属性不同的语义名，例如 `profileBadRecordSelectedTrait`、`profileBadRecordActiveSegment`；不要把 `profileBadRecordTrait`、`profileBadRecordSegment` 写在页面根节点。
- 事件委托不能只依赖 `event.target.closest(...)`。对注入、iframe 或 shadow DOM 可能重定向的控件，先从 `event.composedPath()` 找到真实的、位于当前页面内的匹配控件，再回退到 `closest()`；根节点本身不得作为匹配结果。
- 改名时必须在首个事件处理和渲染前迁移旧 `dataset` 字段，并删除旧属性，防止已打开的旧页面继续截获点击。
- 子页面使用独立 `mode`（例如人物档案事件页）时，所有普通分页的 `active` 判定都必须显式排除该 mode；不要为了消除双选而清空原分页状态，退出子页后应能恢复上次普通分页。
- 有“进入子分页后再切换”路径的应用，验证至少覆盖：进入子页 → 点击不同子项 → 点击普通主标签离开子页。若该路径依赖 MVU 值，本地 `127.0.0.1` 预览须提供隔离的内存变量夹具；它只能在缺少酒馆变量接口时启用，绝不能覆盖真实聊天变量。

### 前端存储导入/导出兼容规约

设置应用、邂逅、成就任务、地点、课程表覆盖、收藏角色、事件回忆/重温等前端存储只要支持导入/导出，就必须默认兼容旧版聊天记录和旧版导出 JSON。

- 导出字段遵循“只加不删、不改旧名”的原则。新增能力优先追加新字段或新版本标记，不重命名旧字段。
- 导入读取必须宽松：同时接受当前字段名、旧字段名、旧数组/对象形态和缺省字段；缺失字段用当前默认值补齐。
- 非必要不删除、改名或改变旧字段含义。确实必须删改时，必须同时实现旧字段别名读取、迁移函数或回退路径，并在验证点里列出旧版样例。
- 旧字段即使当前 UI 不再展示，也不应在导入时静默丢弃，除非它会造成变量错误、重复扣费、重复领奖或明确的安全/一致性问题；丢弃时要写明原因和兼容策略。
- 导入覆盖类操作必须提示用户用于旧版聊天记录迁移；能合并的场景优先合并，不能合并时明确说明覆盖范围。
- 专门 agent 修改前端存储 schema 时，任务合同里的“必须保留”要列出旧字段，“验证点”要包含至少一个旧版导出样例或旧字段扫描。

### 当前变量读取与历史快照

- 前端需要读取 MVU 时，优先读取当前楼层/当前 swipe 的 MVU 数据；只有没有可用 MVU 接口时，才回退到消息快照或本地缓存。
- 回退到历史快照必须带上来源标记和时间/楼层判断，不得让上一楼或上上楼的快照覆盖当前 MVU。
- 重 roll、重新处理变量、重新读取初始变量这类按钮要先清理或重新绑定本轮操作缓存；不能把旧暂存和当前输入混成一轮。
- localStorage 只保存前端 UI 状态、图片、导入导出数据和必要缓存；涉及资源结算、线路推进、角色状态的读取不能优先使用 localStorage。

## 5. 酒馆助手脚本 Agent

职责：

- 维护 `data.extensions.tavern_helper.scripts` 内的酒馆助手脚本。
- 处理 MVU 事件监听、跨日补救、变量初始化、自动修复、脚本依赖/CDN 清理。
- 判断脚本是否应该继续存在，还是交给前端或世界书。
- 审计脚本是否会在重 roll、swipe 切换或重新处理变量时读到上一楼消息；涉及历史消息读取时必须注明读取范围和回退顺序。

主要文件：

- `scripts/finalize-card-v1_6.mjs`
- 酒馆助手相关文档链接，只在需要确认接口时打开

输出必须包含：

- 脚本名和 id
- 触发事件
- 读写变量路径
- 是否引入外部链接/CDN
- 是否和前端/世界书功能重叠

边界：

- 不写 UI。
- 不写剧情规则。
- 不做可由前端轻量完成的每帧/每轮重扫描。
- 不让脚本自动补写会影响剧情判断的资源、角色状态或线路状态；这类补写必须来自前端锁定操作或 AI 的 JSON Patch。

## 6. EJS 审计 Agent

职责：

- 横跨变量、世界书、邂逅导入资产和动态提示词，专门审计 EJS 语法、变量路径、输出范围和 token 负担。
- 确认动态发送给 MVU 更新模型的变量是“必要且具体”的字段，而不是完整 `stat_data` 根对象。
- 检查当前卡世界书和会被前端导入的邂逅角色包世界书，避免只检查已启用条目。

主要文件：

- `scripts/finalize-card_v1_6.mjs` / `scripts/finalize-card-v1_6.mjs`
- `scripts/mirror-frontend.mjs` 中角色包导入与动态世界书写入逻辑
- `public/frontends/hypnosis-app/assets/encounter`

参考文档：

- AI EJS 动态发送提示词：<https://stagedog.github.io/%E7%BB%9C%E7%BB%9C/%E6%95%99%E7%A8%8B/%E6%89%8B%E5%86%99mvu%E5%8F%98%E9%87%8F%E5%8D%A1/%E5%8A%A8%E6%80%81%E5%8F%91%E9%80%81%E6%8F%90%E7%A4%BA%E8%AF%8D/#ai-ejs>
- ST Prompt Template 中文参考：<https://github.com/zonde306/ST-Prompt-Template/blob/main/docs/reference_cn.md>

输出必须包含：

- 哪些 EJS 条目/导入资产被检查
- `getvar(...)` 路径是否和当前变量合同一致
- 是否存在 `setvar(...)`、`incvar(...)`、`decvar(...)`
- 是否存在顶层 `const` 重名、未闭合模板、无兜底路径、完整根对象输出
- 是否会漏发 MVU 更新模型需要的变量，或发送太多无关变量

边界：

- 不设计新变量；需要新字段时转变量 agent。
- 不决定剧情规则；规则冲突转世界书 agent。
- 不改 UI 交互；导入按钮、暂存区和前端存储转正则/前端 agent。
- 审计角色包时按项目前端实际加载的包源为准；导出文件、旧聊天世界书或下载目录里的 JSON 只能作为对照，不能覆盖当前源。

- 处理本地 git 保存、回退、分支/提交整理、本地 8000 端口酒馆同名卡替换和同名聊天记录清理。

主要文件/路径：

- 当前仓库 `.git`
- `/tmp/hypnosisapp5-dist`
- `public/cards/催眠app二改MVU v*.png`
- 本地 SillyTavern 端口对应的 `data/default-user/characters` 与 `data/default-user/chats`

输出必须包含：

- source HEAD、dist HEAD、是否 dirty
- 发布/回退使用的 commit
- 是否 force push / 是否删除聊天记录 / 是否替换本地卡
- 验证命令和结果

边界：

- 不设计功能，不改世界书/前端逻辑。
- 不在未确认目标 commit 时执行 destructive 操作。
- 需要清理远程历史时必须使用明确基点和 force-with-lease，且先说明会保留哪些补丁、删除哪些提交。

## 8. 远程发布 Agent

职责：

- 只在用户明确说“发布远程”“远程”“发布版”等发布意图时启动。
- 专门负责 dist/CDN 发布与发布版 PNG 回写；不设计功能、不修业务逻辑、不手动改生成物。
- 使用项目发布脚本完成全部远程操作，不能手写 `rsync`、`git -C /tmp/hypnosisapp5-dist ...`、手动改 CDN URL 或手动复制 PNG。

固定入口：

```bash
node scripts/publish-card.mjs
```

允许的变体：

```bash
HYPNOOS_RUN_MIRROR=1 node scripts/publish-card.mjs
```

仅当统筹 agent 明确要求“发布时顺便重新生成桌面端”时使用该变体；默认发布当前已经验证过的 `public/frontends/hypnosis-app/`。

发布前置条件：

- 如果本轮改过 `scripts/mirror-frontend.mjs` 或前端资源，统筹 agent 必须先运行：
  - `node --check scripts/mirror-frontend.mjs`
  - `node scripts/mirror-frontend.mjs`

  - `node scripts/build-phone-frontend.mjs`

  - `node --check scripts/finalize-card-v1_6.mjs`
  - `node scripts/finalize-card-v1_6.mjs`
- 发布前必须跑 `npm run verify:card`。它会同时检查本地版与发布版 PNG，并解析内联前端脚本；失败时不得发布。

1. 运行 `node scripts/publish-card.mjs`。

   - 最终只向用户报告通过验证的新 commit。

输出必须包含：

- dist commit 完整哈希或短哈希
- 桌面端 CDN URL
- 手机端 CDN URL

- 是否改动主仓库源码、是否推送主仓库；默认答案应为“没有，除非用户另行要求”

- 不提交或推送主仓库源码，除非用户明确要求。
- 不把 `public/cards/` 发布产物提交到主仓库。
- 不跳过发布后验证；即使发布脚本成功，也必须再跑一次 `npm run verify:card`。
- 不用旧无版本 PNG 名称，不维护第二份发布卡。

## 已知坑位与强制经验

### 前端弹窗与遮罩

- 手机应用内部的确认、提示、未解锁、二次确认弹窗必须使用前端自己的 overlay/card 组件；不要用系统 `alert()` / `confirm()`，尤其是人物档案、警视厅、医院、附身这类会嵌在手机界面里的操作。
- 弹窗只挂到当前应用页或手机根容器内，不能挂到 `document.body`，否则容易盖住右侧暂存区、拦截全局点击或破坏地图/档案页面状态。
- 单按钮提示也要走同一个前端弹窗组件，不要为了“知道了”临时退回 `alert()`。
- 一回合只能操作一次的状态（如附身）必须在确认前检查暂存区，确认后再检查一次，防止双击或异步重入。

### 生成前端的双层转义

- `scripts/mirror-frontend.mjs` 里的源码会进入 `index.html`，再进入 `st-load-inline.html` 和手机端内联脚本；字符串会经过至少一层 HTML/JS 嵌入。
- 在会被内联二次嵌入的 JS 字符串里，不要直接写普通换行或依赖裸 `\n`。需要多段文案时优先使用：
  - `const br = String.fromCharCode(10);`
  - `"第一行" + br + br + "第二行"`
- 任何改动前端文案、弹窗、世界书导入模板或动态脚本后，都必须跑 `npm run verify:card`；该验证会解析内联脚本，能抓到 `Invalid or unexpected token`。
- 如果发布后才发现内联脚本解析错误，必须修源脚本、重新生成前端、重新发布一个新的 dist commit，并只交付新 commit。

### 事件委托、滚动和页面状态

- 任何列表项点击后会重渲染页面时，必须保存并恢复相关容器滚动位置；不要只保存 `document` 或页面主滚动。医院、警视厅、邂逅、人物档案这类页面通常有多个内部滚动容器。
- 列表、性格、细分部位、照片/剪影按钮必须使用 `event.composedPath()` + 当前页面内匹配，避免被根节点 `dataset` 或 shadow/iframe 边界误命中。
- 页面根 `dataset` 状态名不得和子控件 `data-*` 选择器同名；这类冲突曾导致“悬停可点、点击无效”“只能点默认项”“切页后按钮失效”。
- 进入子页后再退出普通主分页必须保留主分页 active 状态；事件页、劣迹、改造这类子模式不能把其它主按钮盖死。
- 地图、医院、警视厅这类有独立主题的页面退出时必须恢复原地图主题，不得把紫色/医院色遗留到地图。

### 变量路径与十页结构

- 当前角色变量只认十页对象：`衣着`、`信息`、`状态`、`事件`、`敏感`、`效果`、`劣迹`、`改造`、`物品`、`子嗣`。世界书、EJS、前端、角色包都不得再写旧 `/角色/<名>/档案/...`、英文 `/characters/...`、`/user/status/...`、`/world/...`。
- `衣着` 与 `信息` 不得混写：头发、面部、上衣、下衣只属于 `衣着`；姓名、年龄、社团或职业、身高、体重、三围或阴茎长度、工作价值、绰号和认可状态只属于 `信息`。
- `改造`、`物品`、`子嗣` 都是正式角色页，不是临时扩展字段。改造按角色/大部位/细分部位存；物品只按 `持有` 单组存，旧 `刷新` 需合并删除；子嗣按 `是否妊娠中`、`生产数量`、`子嗣列表` 存。
- 修路径错误时不要在世界书里追加“禁止旧路径”这类提示词；应该从源头删掉旧路径生成、旧角色包初始变量、旧 EJS 输出和旧按钮 payload。
- 变量检查/一键修复必须以当前变量合同为准；不能把旧 schema 的过时字段当必填，也不能把成就写入变量。
- 角色包、邂逅导入、动态插入世界书与默认角色初始变量都要同源更新；不要只修默认四人，漏掉新加角色或邂逅几十个角色。

### 世界书与提示词卫生

- 世界书里只写 AI 需要理解的剧情/变量规则；前端已经完成的 UI 细节、开发者备注、防盗词、发布说明、脚本内部原因不要泄露给世界书。
- `[mvu_update]` 条目要短、机械、无重复句；同一规则不要在多个条目里反复复制，避免变量模型把提示词原样写入变量。
- 需要 AI 生成文本的字段必须明确“AI生成最终描述，不得原样写入用户备注、提示词、JSON 或素材对象”。性格特调和医院改造尤其要写清。
- 线路剧情 `0→1`、`1→2` 必须规定为一个 AI 回复楼层内写完，不允许“待续”造成无限延长。
- 特殊末尾段（派遣中、九鬼监视）要明确独立格式和字数上限，避免吞掉主剧情。
- 固定输出段如果能用 EJS 判定启用，就不要在多个世界书里重复写触发条件；EJS 控制显示，世界书只保留必要表现规则。
- 时空轮转、打工、派遣、线路收束这类格式规则要分清“正文格式”和“变量更新规则”；不要让 MVU 更新模型照抄正文提示。

### 图片、剪影和邂逅资产

- 内置图片、警视厅剪影、医院剪影的源头在前端脚本/资产定义；不要只替换生成 HTML。
- 没有专属警视厅/医院剪影的角色必须有默认通用剪影；自定义角色允许在邂逅里配置专属剪影。
- 邂逅页面图片加载优先分页、懒加载或打开后加载；不要一次性预加载整页所有大图导致卡顿。
- 同一角色不同来源包的排序、重复显示策略要在前端源数据里处理；不要靠用户手动筛。
- 邂逅角色包卡片、角色卡片、场景剪影、人物剪影必须有独立点击目标和 active 状态；场景剪影点击不能回到人设世界书按钮。
- 内置角色包以项目前端源里的 `package.json` 和角色目录为准；同名重复角色按当前前端策略去重，不能把旧导出集合当成最新真源。

### 发布与验证

- 发布远程不是“跑完脚本就结束”。发布前和发布后都要 `npm run verify:card`。
- 发布脚本默认跳过 `mirror`，所以前端改动必须先由统筹 agent 生成好 `public/frontends/hypnosis-app/`；否则会把旧前端发出去。
- 远程发布失败或验证失败时，不要向用户交付失败 commit；修复后重新发布新 commit，并报告新 commit。
- 发布版不应包含本地版正则或测试开场；发布版开场白数量和本地版不同是正常的，但要按用户要求核对。
- 远程发布 agent 只运行 `node scripts/publish-card.mjs` 或经统筹明确的 `HYPNOOS_RUN_MIRROR=1 node scripts/publish-card.mjs`；不要手动 clone、rsync、改 CDN URL 或维护第二套发布目录。
- 主仓库源码提交和 dist/CDN 发布是两件事。用户只说“发布远程”时，默认只更新 dist/CDN 和发布版 PNG，不提交主仓库源码。

### 占位符、悬浮手机与楼层快照

- `<StatusPlaceHolderImpl/>` 只负责暂存卡和注册楼层，绝对不能在每个匹配楼层里加载整份 webpack 前端、MutationObserver 或定时器。完整手机必须是宿主页单例。
- “手机当前查看楼”和“唯一可写楼”是两个不同概念。可写楼必须从聊天 `context.chat` 的最后一个 assistant 消息计算，不得以“已挂载 iframe 的最大 mesid”或 DOM 可见性替代。
- 历史楼读取必须保留显式 `message_id`，写入时若目标不是唯一可写楼就拒绝；禁止把调用者显式传入的历史 `message_id` 静默改成当前楼，否则会把历史快照导入循环覆盖到当前楼。
- 历史楼所有变量读取都返回克隆，防止“先原地改对象，后续 replace 被拦截”时污染宿主活动引用。历史分支只跑纯渲染，不跑迁移、schema 修复、世界书同步、派生变量同步或状态提醒写入。
- 精确楼层无 MVU 快照时显示“无快照”，不允许 `pickBestVariableSnapshot`、最近楼或上一楼兜底。本地缓存只存选中楼键、窗口坐标和模式，不存整份快照。
- 宿主单例的监听、observer、fetch 和 iframe 必须有 `destroy/dispose`；手机重建前取消上一次 fetch，多楼同时注册要合并加载，不得反复下载和解析整份内联前端。
- 测试至少覆盖：宿主只有一个手机 iframe、每楼只有轻量暂存卡、下拉选楼后时间/资源实际变化、历史 `replace/update/set` 被拒绝、切回最新楼后才能操作。

## 冲突裁决

- 变量名、默认值、读写权限：变量 agent 优先。
- UI、暂存、localStorage、MVU 实际读写：正则/前端 agent 优先。
- AI 应如何理解/执行：世界书 agent 优先，但必须服从变量合同。
- 事件监听和自动修复：酒馆助手脚本 agent 优先，但不得覆盖前端已经处理的状态。
- EJS 动态变量输出范围、语法和路径一致性：EJS 审计 agent 优先，但必须服从变量合同和世界书语义。
- 提交历史、本地酒馆替换：Git / 本地版本 agent 优先，但不得自行改功能逻辑。
- 远程 dist/CDN 与发布版 PNG：远程发布 agent 优先，但只能使用发布脚本。
- 跨层冲突无法解决时：统筹 agent 收束为一个最小变更方案。

## EJS 审计规则

EJS 横跨变量、世界书和前端邂逅导入，是独立 agent。只要任务涉及动态变量输出、世界书条目、角色包/邂逅导入、`getvar` 路径、MVU 更新模型 token 范围，就启动 EJS 审计 agent。

EJS 审计 agent 的边界：

- 只负责 EJS 语法、变量路径、输出范围和导入资产一致性，不改 UI 交互和剧情正文。
- 必须核对当前变量合同，尤其是字段改名、只读字段、动态字典和旧版兼容字段。
- 必须同时扫最终卡世界书和会被前端导入的邂逅资产，不能只看当前卡内已启用条目。

EJS 必查项：

- 使用 `getvar('stat_data.具体路径')` 读取具体字段；禁止无条件输出完整 `stat_data` 根对象。
- 动态输出优先用 `<%_ { ... } _%>` 包住作用域，内部用 `print(...)` 输出，避免多个条目拼接后顶层 `const` 重名。
- EJS 条目默认只读：禁止 `setvar(...)`、`incvar(...)`、`decvar(...)` 出现在世界书或邂逅资产里。
- 字段名必须和当前变量一致；例如角色性欲字段使用 `性欲`，不得再通过 `getvar('stat_data.角色.*.发情值')` 读取。
- 对可能不存在的路径使用默认对象、默认数组或空字符串兜底，不让模板因为旧聊天缺字段直接编译或运行失败。
- 修改 EJS 后必须跑 `npm run verify:card`；如果涉及邂逅资产，还要额外扫 `public/frontends/hypnosis-app/assets/encounter`。
- 新增测试开场后，额外核对开场锚点、备用开场数组下标和酒馆助手初始化脚本三者一一对应，普通开场不携带测试专用变量覆盖。

## 低 Token 操作规矩

- 搜索用 `rg`，读取用小窗口 `sed -n` / `nl -ba`，不要整文件 `cat` 大脚本。
- 只读生成 HTML 做验证，不在设计阶段读完整 HTML。
- PNG 元数据只在改 finalizer、世界书、正则或发布前抽检一次。
- 每个专门 agent 最多读 2 个主文件和 1 个验证文件；超过就回报统筹拆任务。
- 专门 agent 不互相长聊，只通过统筹的变量合同和短结论交接。
- 没涉及某层就不启动该 agent。

## 最小验证矩阵

按实际改动选择，不要全量滥跑：

```bash
node --check scripts/finalize-card-v1_6.mjs
node --check scripts/mirror-frontend.mjs
node --check scripts/build-phone-frontend.mjs
node scripts/mirror-frontend.mjs
```

- 默认正则目标是本机 `http://127.0.0.1:5173` 的生成前端；日常验证前确认 `npm run dev` 正在运行。
- 只有用户明确要求“远程发布”时，才启动远程发布 agent 使用 `node scripts/publish-card.mjs` 更新 dist/CDN；除非用户明确要求，不提交或推送主仓库。
- 发布远程前后都必须运行 `npm run verify:card`。如果发布前验证失败，不发布；如果发布后验证失败，修复源脚本并重新发布新的 dist commit。
